# 衝突裁決規則（Orchestrator 用）

當兩個 sub-agent 的輸出矛盾時，Orchestrator 按以下優先序採信。裁決必須寫進最終報告的「衝突登記」區，明確列出矛盾雙方、採信誰、為什麼——**不可把衝突抹平成「綜合方案」**。

## 採信優先序

1. **來源可信度**：`red_team` > `game_simulator` > `lens_analyst` > `entity_modeler`
   - 理由：紅隊是隔離的、以失敗為目標的視角，最不易被主線敘事收編；博弈模擬揭示互動層湧現；鏡頭分析是單點視角；實體建模是結構骨架。
2. **風險不可逆性**：涉及「不可逆風險」的輸出 > 涉及「成本」的輸出
   - 不可逆風險（監管認定、控制權讓渡、跨法人資金流）一旦發生無法回收；成本可以再賺。不可逆優先。
3. **鏡頭層級**：平台動態鏡頭 > 經濟學鏡頭（當兩者衝突時）
   - 平台動態是結構性長期力量；經濟學常是短期成本視角。長期結構壓過短期成本。

## 裁決輸出格式

每筆衝突一個區塊：

```
## 衝突 #N
- 衝突雙方: {agent_a} 主張 X / {agent_b} 主張 Y
- 矛盾本質: 一句話
- 採信: {winner}
- 採信規則: 優先序 1/2/3 中的哪條
- 對最終方案的影響: 採信後方案如何調整
```

## 反模式

- **抹平式整合**：「兩邊都對，綜合一下」——這會把信號噪聲化。衝突本身就是 sub-agent 設計要產生的信號，必須顯式裁決。
- **Orchestrator 自行分析**：Orchestrator 不做認知，只套規則裁決。若三條規則都無法裁定，標記為「未決衝突」交給人類決策者，不要自己編理由。
- **向上採信忽視不可逆**：即使 red_team 判定致命，仍以成本理由否決它——違反規則 2。不可逆風險永遠壓過成本。
