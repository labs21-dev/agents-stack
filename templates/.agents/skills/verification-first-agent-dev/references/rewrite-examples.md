# 改寫範例庫：從一句話到驗證劇本

每例三段：原話 → 劇本 → 劇本裡的關鍵判斷。抄結構，不抄內容。

## 例 1：功能新增（歷史記錄搜索）

原話：
> 給歷史記錄增加搜索功能

劇本：
> 完成歷史記錄搜索功能。啟動開發版本。創建三條測試數據。
> 搜索其中一個關鍵詞，確認結果只出現匹配內容。
> 清空關鍵詞，確認完整列表恢復。
> 測試中文、英文和空搜索。
> 任何一步失敗，繼續修復直到驗證全部通過。

關鍵判斷：清空恢復（狀態可逆性）+ 中英文空（邊界）+ 修到過（失敗協議）。

## 例 2：Bug 修復

原話：
> 刪除歷史記錄失敗，修一下

劇本：
> 修復刪除歷史記錄失敗的問題。
> 先啟動開發版本，創建三條記錄，親自復現這個 bug（操作 + 記錄實際錯誤現象與日誌）。
> 找到根因後修復。然後驗證：
> 刪除單條 → 列表即時更新且計數正確；刪除後重啟應用 → 記錄仍已刪除；
> 連續快速刪除兩條 → 不崩潰、兩條都消失；刪除最後一條 → 空狀態正常顯示。
> 全部通過後，報告根因一句話 + 每步驗證結果。

關鍵判斷：**先復現再修**（不許 agent 憑猜測改）+ 持久化驗證（重啟後仍刪除）+ 根因報告（沉澱素材）。

## 例 3：性能問題

原話：
> 10000 條記錄搜索很卡

劇本：
> 修復 10000 條記錄時搜索卡頓。先自己重現：造 10000 條測試數據，抓 Performance Trace，
> 記錄卡頓發生的具體環節（輸入延遲 / 渲染 / 查詢）和數字（輸入到結果的 ms）。
> 修復後重跑同一 trace，輸入到結果必須 < 100ms，且中文關鍵詞同樣達標。
> 報告前後對比數字 + 你改了什麼。

關鍵判斷：性能必須是**數字斷言**（<100ms），不是「感覺不卡了」；修前修後同一把尺。

## 例 4：狀態 / 生命週期 bug

原話：
> 窗口重新打開後狀態丟了

劇本：
> 修復窗口重開後狀態丟失。驗證：設置一個可觀察狀態 → 關閉窗口 → 重開 →
> 狀態必須恢復。再測：應用完全退出重啟 → 狀態恢復；狀態保存失敗（模擬磁盤只讀）→
> 應用不崩潰且有日誌。報告狀態存到了哪裡、什麼時機寫入。

關鍵判斷：生命週期 bug 的斷言在「重啟之後」，劇本必須含跨重啟步驟；補一個故障注入邊界。

## 例 5：重構（有 feature map 時）

原話：
> 把 cart 模塊的價格計算邏輯整理一下

劇本：
> 重構 cart 價格計算。先讀 .agent/feature-map.md 的 Cart 卡確認入口與驗證步驟。
> 重構前：跑該卡全部驗證步驟並記錄通過（基線）。
> 重構後：重跑全部驗證步驟，全部通過才算完成。行為不得變化——
> 同樣輸入必須產出同樣價格。報告 diff 摘要 + 前後驗證結果對比。

關鍵判斷：重構的驗證 = **基線先行**（重構前先證明現在是對的）+ feature map 卡直接消費。

## 劇本五要素檢查表（寫完自查）

- [ ] 造數據：數量、內容、多樣性明確
- [ ] 正路徑：斷言查**結果**，不是無報錯
- [ ] ≥2 個真實邊界（空/中文/大量/大小寫/故障注入，挑適用的）
- [ ] 失敗協議：修到全部通過，不是「試試看」
- [ ] 環境工具：每步都能機器執行；「人工確認」步驟已消除或明確標記為人驗收點
