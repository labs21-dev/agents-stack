# 路由機制詳解

路由表每一格的「為什麼」。改動路由判定條件前先讀這份。

## M1 — Prompt 不教判斷，只做選擇

原則的有效形式是「對模型已具備的行為分佈做錨定」：一句話把分佈裡已存在的
行為拉到前面。它**不是**把新能力寫進模型——那是訓練期（RLHF/CAI）的事，
兩者常被混為一談（見 anti-patterns.md #4）。

推論：
- 原則的採用前置檢查是 **capability probe**（見下）。未驗證就寫原則，
  失敗時看起來像「模型不聽話」，實際是規格形式選錯。
- 原則**不可跨模型移植**：移植性與模型能力差距成反比。弱模型沒有原則
  假設的底層判斷，同一句原則對它退化為形容詞；帶觸發條件的規則或範例
  反而更有效。跨模型搬**結構與路由結果**，每個模型重跑 capability probe。

## M2 — Prompt 內一切皆 advisory

系統提示詞是 in-context 的 token，不是執行環境。模型對它近似遵循（probabilistic
adherence），不保證遵循。因此：

- 紅線（不可協商、失敗成本不可逆）放 prompt 等於把法律寫成建議。正確去處是
  harness：審核閘、權限邊界、deny-list、程式檢查。prompt 內的 `NEVER`
  保留——作為**降低發生率的提醒**——但永遠不是唯一防線。
- Priority stack（P0 安全 > P1 正確 > P2 格式 > P3 風格）只有在 harness
  也按此序強制時才是真的優先序，否則是願望清單。

## M3 — 注意力天花板不豁免原則

稀缺資源是 context 注意力，不是 token 數。規則牆會稀釋注意力，**原則牆同樣
會**——原則的優勢只是壓縮率（一句話覆蓋更多 case），不是免疫。實務天花板
約 2k token 的規則/原則總量；超過時：
1. 重新路由（多數條目本該在 validator/harness）；
2. 降階合併（多條同源規則 → 一條原則 + 範例）；
3. 下沉到 skill / tool / eval（規格分層）。
**不要**用「改寫得更精煉」繞過——壓縮措辭不改變注意力負載的量級。

## M4 — Cache 前置 vs mid-context 遵循衰減：prompt 內無解的衝突

已知現象：長 context 中，前置與中段指令的遵循率會衰減（lost-in-the-middle）。
同時 prompt cache 要求穩定內容前置、可變 context 後置。兩者拉扯：

- 前置吃 cache → 中後段任務遵循衰減
- 近端重述 → cache 失效、成本上升

**這個衝突在 prompt 內部無解**，它是「該約束外移到 harness」的證據：
長任務會漂移的行為 → harness 重注入（階段性把關鍵約束塞回近端 context）、
狀態檢查（每階段驗證產物是否符合）、階段閘（不合不放行）。
Prompt 內可以做的緩解：穩定塊前置分節（吃 cache）+ 範例錨定（分佈錨定
比抽象指令抗漂移），但這只是緩解。

## M5 — 修訂爆炸半徑

規則逐條加逐條驗，改一條影響一個 case；原則改一句話影響它覆蓋的**所有**
case。這是原則的隱性審查成本。管理方式：
- 每條原則在 worksheet 綁定「覆蓋的 eval case」——沒有 case 覆蓋的原則
  不准入 prompt（不可證偽的品味）。
- 修訂原則時，重跑其覆蓋 case；worksheet 是修訂的 blast-radius 地圖。

## M6 — 範例 > 抽象原則（當有生產失敗樣本時）

範例做的是分佈錨定：直接展示「輸入 → 推理 → 正確動作」，效應量比抽象
原則穩（原文引的 54% relative 屬此類，未復現，方向可參考不作承重牆）。
要求：
- 來自**生產失敗**，不是想像的 happy path（後者錨定的是沒問題的行為，
  等於沒訓練）。
- 帶顯式推理鏈（為什麼這是對的動作）。
- 1–3 個；過多佔注意力預算且引入過擬合。
- 複雜指引放 system prompt，不要碎在 tool description 裡（tool schema
  該寫「何時不要用」這類短政策，不承載流程）。

## Capability probe（路由表「模型已具備該判斷」欄的驗證法）

最低成本版本，目標模型上跑：

1. **遵循率探針**：該原則 + 20 個未見 case（從生產失敗或對抗樣本取），
   量遵循率。有對照組更佳：同一批 case 跑「無此原則」版本做 A/B。
2. **判定**：遵循率顯著高於對照 → 判斷在分佈內，原則成立；接近對照或
   兩者都低 → 判斷不在分佈內，**降階**：改成帶觸發條件的規則，或改用
   範例錨定，或外移到 harness。
3. 注意：探針不通過的修復動作是**換規格形式**，不是改原則措辭。反覆改
   措辭救不了能力缺口的約束。

## 路由表的升階與降階規則

執行層強度：`validator/schema > harness > prompt 範例 > prompt 原則`。

- **升階優先**：約束符合多層條件時選最高層。例：紅線且可機械檢測 →
  validator，prompt 內 NEVER 只是備份提醒。
- **降階僅在**：更高層做不到（判斷本質開放、無法程式化）或成本過高
  （檢查程式的維護成本超過失敗成本）。
- **降階必須留升級路徑**：worksheet「未來升級」欄記錄——今天寫不出
  檢查程式 ≠ 永遠寫不出；每次事故後重訪此欄。

## 機制的最低成本驗證法（本 SOP 的防自證設計）

| 機制 | 驗證法 |
|---|---|
| M1 選擇而非教學 | 同一原則在強/弱模型各跑 20 未見 case，比較遵循率差 |
| M3 原則也吃天花板 | 10k+ context 探針集：3 原則 vs 15 規則表達同一行為，量遵循率 |
| M4 衝突與外移收益 | 同一長任務：前置原則 vs harness 重注入，量中後段遵循率 |
| M6 範例 > 原則 | 任一現有 eval 集 A/B：加範例 vs 加原則，20 case |
